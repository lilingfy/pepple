# 会话管理规范

## 概述

会话管理控制陪练场的完整生命周期，包括开始、继续、重启、结束四种状态流转。

## ADDED Requirements

### 需求:必须支持 start 语义
首次进入场景时必须创建新会话，不携带 sessionId，后端返回新 sessionId 和开场白。

#### 场景:首次进入场景
- **当** 用户选择场景且未携带 sessionId
- **那么** 系统调用 `POST /api/simulator`（无 sessionId），创建新会话，返回 sessionId 和 AI 开场白

### 需求:必须支持 turn 语义
继续当前会话时必须携带 sessionId 和用户消息，后端返回 AI 回复和情绪分析。

#### 场景:继续对话
- **当** 用户在会话中发送新消息
- **那么** 系统调用 `POST /api/simulator`（携带 sessionId + message），返回 AI 回复和 rightPanel 分析数据

### 需求:必须支持 restart 语义
重启当前场景时必须携带原 sessionId，后端清空历史并返回新 sessionId，重新开始对话。

#### 场景:用户重启会话
- **当** 用户点击"重启本局"
- **那么** 系统调用 `POST /api/simulator`（携带原 sessionId + restart 标记），后端返回新 sessionId，消息列表清空，显示新开场白

#### 场景:切换场景自动重启
- **当** 用户在对话中切换到另一场景
- **那么** 当前会话结束，自动以 start 语义创建新场景会话

### 需求:必须支持 end 语义
结束演练时必须调用 end 接口，获取完整会话总结。

#### 场景:用户结束演练
- **当** 用户点击"结束演练"
- **那么** 系统调用 `POST /api/simulator/[sessionId]/end`，返回最终得分、总体反馈、改进建议、会话时长

#### 场景:结束后禁止发送消息
- **当** 会话已结束（调用 end 后）
- **那么** 输入区禁用，用户无法继续发送消息

### 需求:会话状态必须可追踪
系统必须维护当前会话状态：idle（空闲）、active（对话中）、ended（已结束）。

#### 场景:状态流转检查
- **当** 用户从选择场景 → 发送消息 → 结束演练
- **那么** 会话状态按 idle → active → ended 流转，UI 相应更新

### 需求:必须处理会话超时
长时间无操作的会话应提示用户，可选择继续或结束。

#### 场景:会话超时提示
- **当** 会话超过 30 分钟无活动
- **那么** 显示超时提示，用户可选择"继续练习"（保持会话）或"结束演练"
