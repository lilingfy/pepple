## Context

首页是 Pebble AI 的首个生产级页面，也是 `TB-005` 设计系统和 `PageShell` 的第一批消费方。当前约束已经足够明确：第二版首页 HTML 是前端真相源，页面必须沿用既有视觉语言和区块顺序，同时优先复用共享组件，不能为首页单独开一套页面结构。

本次变更只覆盖 `/` 页面本身，不引入后端新接口，不修改翻译器、陪练场或急救呼吸页面的行为。首页的核心价值是承接品牌入口、解释产品价值，并把用户稳定导向三个功能页。

## Goals / Non-Goals

**Goals:**
- 用 `PageShell` 和 `MainHeader` 组成首页统一页面壳。
- 按第二版首页设计稿落地导航栏、Hero、统计区、功能预览区和页脚。
- 复用 `PebbleButton`、`GlassCard`、`StatusPill` 等设计系统组件，避免首页自定义重复样式。
- 保证首页在桌面端与移动端都有稳定的响应式退化行为。
- 为首页建立可回归的测试边界，覆盖渲染、跳转、文案和可访问性。

**Non-Goals:**
- 不新增后端 API。
- 不实现翻译器、陪练场、急救呼吸的业务逻辑。
- 不重做设计系统本身，设计系统已由 `TB-005` 交付。
- 不改变第二版首页 HTML 的核心信息结构和文案方向。

## Decisions

### 1. 采用 App Router 页面组合，而不是单页大组件
首页将由 `apps/web/app/page.tsx` 作为路由入口，组合若干页面区块组件，而不是把所有结构塞进一个大文件。这样可以把导航、Hero、统计、功能卡片和页脚分别测试，也便于后续局部替换。

备选方案：
- 单文件页面。缺点是测试和维护成本高，区块之间耦合重。
- 传统页面模板。缺点是和现有 Next.js App Router 结构不一致。

### 2. 共享壳层优先，首页只做内容编排
首页顶部导航和整体容器直接复用 `MainHeader` 和 `PageShell`，首页自身只负责内容排列与少量首页专属视觉。这样能保持四个主页面的结构一致，也能避免首页演进把共享壳层冲散。

备选方案：
- 首页自带独立导航。缺点是会制造与其他页面不一致的壳层规则。

### 3. 动效分层，静态内容先稳定
Hero 背景、标题轻动效和统计数字动画只作为增强层，不应阻塞内容首屏可读性。主体内容必须在无动画和低性能设备上仍可完整阅读。

备选方案：
- 全屏强动效首屏。缺点是性能风险高，也容易掩盖信息层级。

### 4. 组件复用优先于首页专用样式
按钮、卡片、状态标签、输入壳等视觉语言直接使用设计系统组件。首页只允许少量区块级修饰，避免出现首页自己定义的“平行设计系统”。

备选方案：
- 首页自定义按钮和卡片。缺点是会破坏设计系统一致性。

### 5. 测试以行为和结构为主，不依赖实现细节
首页测试聚焦于页面渲染、导航跳转、主文案、区块存在性、响应式退化和无障碍语义，不锁死具体 DOM 细节。这样设计调整时测试不会频繁误报，但关键契约仍然可验证。

## Risks / Trade-offs

- [首页区块过多导致首屏负担变重] → 采用分区懒渲染和轻量动效，保证 Hero 区先稳定展示。
- [共享壳层改动影响首页] → 把页面壳升级放到 `TB-005` 的规范边界内，通过回归测试兜住。
- [首页文案和功能卡片与后续页面不一致] → 使用 taskbook 和执行清单中的路由与 CTA 作为唯一来源。
- [动画在低端设备上拖慢页面] → 动效只使用 transform 和 opacity，并提供 `prefers-reduced-motion` 退化。

## Migration Plan

1. 以 `TB-005` 现有设计系统和页面壳作为前置依赖。
2. 先落 `app/page.tsx` 和首页区块组件的测试骨架。
3. 再实现首页路由和内容编排。
4. 最后补充响应式、可访问性和回归测试。
5. 如果首页实现与设计稿存在明显偏差，优先修正文档或区块实现，不回退共享设计系统。

## Open Questions

- Hero 区 CTA 是否需要保留“演示视频”占位入口，还是直接跳转到实际功能页。
- 首页统计数据是否完全静态，还是在后续阶段从服务端汇总读取。
- 功能预览卡片是否需要跟随后续功能页状态显示“已完成/开发中”。
