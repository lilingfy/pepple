## 上下文

Pebble 当前已经有四个页面任务书和三份第二版前端 HTML，但还没有一个可执行的设计系统实现边界。现状风险有三类：第一，首页、翻译器、陪练场和呼吸页会各自复制样式，导致颜色、圆角、阴影、排版和动效漂移；第二，页面在并行开发时会不断发明新的基础组件，后续很难统一；第三，后端契约虽然已经在 TB-006 中定义，但前端如果没有稳定页面壳和组件基线，接口稳定也无法转化为稳定体验。

该变更直接服务 `TB-005`，同时为 `TB-001` 到 `TB-004` 提供统一的视觉和结构基础。约束条件很明确：第二版 HTML 是前端真相源，设计系统必须以这些页面的共同元素为抽象基础；技术栈固定为 `Next.js 15 + React 19 + TypeScript + Tailwind CSS 4 + Framer Motion + shadcn/ui`；实现必须遵循 TDD，并为后续页面开发保留清晰的复用边界。

## 目标 / 非目标

**目标：**

- 建立一套可测试、可复用的 Pebble 设计令牌，包括颜色、字体、间距、阴影、鹅卵石圆角和玻璃拟态基础样式。
- 建立基础组件层，包括按钮、卡片、输入容器、状态条、标签、导航元素和页面壳容器。
- 建立四个页面共享的布局基础，包括主导航、内容容器、分栏规则、移动端堆叠规则和页面底部结构。
- 建立前端测试基线，使页面在进入实现阶段前就能复用稳定组件和稳定断点规则。

**非目标：**

- 不在本变更中完成首页、翻译器、陪练场和呼吸页的完整页面业务实现。
- 不在本变更中定义后端 API、DTO 或持久化逻辑。
- 不引入新的 UI 框架或替换现有 `Tailwind`、`Framer Motion`、`shadcn/ui` 组合。
- 不把页面私有业务状态放进设计系统层。

## 决策

### 决策 1：以设计令牌 + 基础组件 + 页面壳三层结构实现设计系统

采用三层结构：
- 设计令牌层：颜色、字体、圆角、阴影、间距、动画时长和层级。
- 基础组件层：`PebbleButton`、`GlassCard`、`PebbleInputShell`、`StatusPill`、`SectionLabel` 等。
- 页面壳层：`MainHeader`、`PageShell`、`SidebarLayout`、`CenteredStageLayout` 等。

选择这个方案，是因为第二版 HTML 的共性主要集中在这三层。如果直接从完整页面抽组件，抽象会被页面私有逻辑污染；如果只做颜色和字体令牌，又不足以降低后续页面开发成本。

备选方案：
- 只做设计令牌，不做组件和页面壳。问题是后续页面仍会自行组装结构，复用价值低。
- 直接从四个页面中同时抽取所有组件。问题是初期范围过大，容易把业务逻辑和视觉复用混在一起。

### 决策 2：优先抽取四个页面共有元素，不为单页特例提前建模

设计系统第一轮只收纳在四个页面中反复出现的稳定元素，例如胶囊按钮、玻璃卡片、鹅卵石图标容器、主导航、状态标签、基础输入壳。像翻译器的建议卡片偏移交互、陪练场的分数圆环、呼吸页的波纹层这类页面特有能力，保持在页面模块内。

选择这个方案，是为了遵守 YAGNI。当前最重要的是建立复用基线，不是预先把所有未来组件都发明出来。

备选方案：
- 一次性建立完整组件库。问题是成本高，需求边界并不稳定。

### 决策 3：视觉契约以第二版 HTML 为准，代码实现通过测试冻结组件 API 和关键状态

设计稿决定视觉目标，测试决定实现边界。每个基础组件至少验证：
- 默认渲染
- 关键状态
- 交互状态
- 桌面端和移动端布局表现

选择这个方案，是因为这个项目的风险不在“能不能做出来”，而在“做出来后每页都不一样”。通过测试锁住组件契约，比依赖口头约定更可靠。

备选方案：
- 只依赖人工 code review。问题是无法有效拦截回归。

### 决策 4：网络与业务逻辑留在页面 client 层，设计系统保持无业务副作用

设计系统组件不得直接发起 `fetch`、读写业务 store 或理解后端语义。组件只接收清晰 props，页面模块负责把业务数据映射到展示层。

选择这个方案，是为了让 `TB-006` 的后端契约演进不会反向污染设计系统，并保持组件在首页、翻译器、陪练场、呼吸页间的可复用性。

备选方案：
- 把 API 调用能力封进通用组件。问题是会把组件变成不可重用的业务单元。

## 风险 / 权衡

- [设计抽象过早] → 第一轮只覆盖共性元素，不抽取页面特例组件。
- [视觉还原与组件复用冲突] → 先保证令牌和页面壳一致，再允许页面组件在不破坏系统的前提下扩展。
- [响应式规则不一致] → 在页面壳层统一断点和列布局，不允许页面自己发明新的主布局规则。
- [测试维护成本上升] → 只为基础组件、页面壳和关键状态建测试，不为纯装饰细节写脆弱快照。
- [shadcn/ui 与自定义视觉冲突] → 使用其可访问性和基础行为，外观统一通过 Pebble 令牌和封装层处理。

## 迁移计划

1. 先建立设计令牌导出和基础样式入口。
2. 再建立基础组件层，并补齐对应测试。
3. 再建立页面壳层，锁定导航、容器和布局规则。
4. 将 `TB-001` 到 `TB-004` 的页面实现改为优先依赖设计系统组件。
5. 如果某个页面已存在临时组件，则逐步收敛到设计系统组件，不做一次性大爆炸替换。
6. 若出现严重视觉偏差，可回滚到上一个设计系统提交，同时保留页面业务逻辑不变。

## 开放问题

- 首页和其他页面是否共用完全同一套主导航，还是保留首页特化导航样式。
- `Public Sans`、`Noto Serif SC`、`Noto Sans SC` 的加载方式是统一走 `next/font` 还是保留现有字体方案。
- 是否需要在设计系统第一轮就提供主题变量导出，供后续非 Web 端复用。
